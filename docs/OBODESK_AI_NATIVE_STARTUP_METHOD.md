# OboDesk AI-Native Startup 方法论上下文

本文档基于 `docs/reference/FOUNDERS_PLAYBOOK_CN_EXTRACT.md` 提炼，用于 OboDesk 后续产品、工程、增长和运营决策。它不是原文整理，而是把 AI-Native Startup 的方法论转化为 OboDesk 可长期复用的工作上下文。

核心判断：AI-Native 不是“用 AI 更快做完所有事”，而是把 AI / Agent 作为研究、工程、运营和组织系统的基础设施，同时把创始人的注意力从低阶执行转移到问题判断、证据解释、取舍和编排上。

## OboDesk 当前阶段判断

当前 OboDesk 不应直接判定为发布阶段或规模化阶段。虽然已经具备 Shopify 独立站、Product Center、商品事实核验、飞书、Codex 和初步自动化基础，但仍缺少足够的真实市场证据：

- 目标用户问题证据；
- 内容转化证据；
- 加购与购买证据；
- 客服与用户反馈证据；
- 复购、推荐或稳定渠道证据。

因此，当前阶段应定义为：证据化 MVP 阶段。

这个判断的实际含义是：OboDesk 当前的首要任务不是扩大自动化、扩张渠道或构建复杂运营体系，而是围绕真实用户证据建立 MVP 反馈闭环。所有 AI / Agent 工作都应优先服务于问题验证、内容转化验证、购买路径验证、商品信息可信度验证和用户反馈收集。

## 总原则

1. 先验证真实问题，再建造。OboDesk 的每个重要功能都必须对应一个具体用户、具体场景、具体痛点和可观察证据。
2. 原型不是验证，用户证据才是验证。可运行 demo 只能帮助对话，不能替代用户访谈、行为数据、留存、付费和推荐。
3. AI 会放大确认偏误。让 Agent 找支持性材料很容易，真正有价值的是让它系统性寻找反证、替代解释和失败路径。
4. 创始人是 Orchestrator，不是低阶执行者。Agent 负责研究、归纳、生成、测试、分诊、自动化；创始人负责判断什么值得做、什么不该做、何时停止。
5. Agentic 编程必须有范围、架构和持久上下文。OboDesk 的 AI 编程工作必须依赖清晰任务边界、架构约束、决策记录和项目级上下文，而不是临场发挥。
6. 自动化不能早于流程稳定。没有被人工跑通、验证过、边界清楚的流程，不应直接自动化。
7. 对抗性思考必须成为固定工作流。任何产品假设、增长假设、市场判断、架构决策，都要有反方审查。
8. 不要把执行速度误认为商业验证。更快上线只说明建造能力提高，不说明需求真实、用户愿意付费、渠道可重复。

## 四个阶段

## 1. 想法阶段

### 阶段目标

确认 OboDesk 是否正在解决一个真实、具体、足够强烈的问题。这个阶段的重点不是设计完整产品，而是把模糊直觉变成可验证假设：谁有这个问题，问题发生在哪里，频率多高，损失多大，现有替代方案为什么不够好。

对 OboDesk 来说，任何“应该做”的功能设想，都要先变成问题假设。例如，不应停留在“用户需要更好的工作台”，而要明确到“哪类用户在什么任务中，因为现有流程的什么断点，付出了多少时间、成本或错误风险”。

### 退出标准

- 已经确认一个清晰目标用户群，而不是泛泛的“所有人”。
- 已经通过真实用户对话、公开反馈、竞品评论、社区讨论或现有行为数据证明问题存在。
- 已经理解用户当前怎么解决这个问题，以及他们为什么对现状不满意。
- 已经找到问题与方案的初步匹配，而不是只证明创始人的想法能被做出来。
- 已经记录主要反证：哪些信号说明这个问题可能不够痛、市场可能太窄、替代方案可能已经足够好。

### 常见失败模式

- 把“我们能做一个原型”误认为“市场需要这个产品”。
- 让 AI 只搜集支持性资料，形成看似严谨但方向错误的论证。
- 问用户“你会不会用”，而不是追问他们上一次真实处理该问题的过程。
- 过早讨论功能清单、技术方案和视觉呈现，跳过问题验证。
- 低估竞品和替代流程，把用户当前做法误判为“落后”，而不是理解其约束。

### AI / Agent 应该做什么

- 把创始人的初始想法改写成可测试的问题假设。
- 为每个假设生成反方论证、失败场景和需要验证的关键条件。
- 梳理竞品、替代方案、公开用户反馈、社区讨论和行业趋势。
- 设计用户访谈提纲，避免诱导性问题，强调过去行为而非未来承诺。
- 汇总访谈记录，提取重复痛点、用户原话、分歧和未被验证的假设。

### 创始人必须亲自判断什么

- 这个问题是否值得 OboDesk 长期投入。
- 用户痛点是真正高频高价值，还是只是访谈中听起来合理。
- 哪些用户反馈代表目标群体，哪些只是个别噪音。
- 是否应该继续、收窄、转向，或停止当前方向。
- OboDesk 的独特优势是否真的能解决这个问题，而不是只做出另一个同质工具。

### 对 OboDesk 的实际含义

OboDesk 当前不应把产品路线图建立在“AI 可以快速实现”的基础上，而应建立在“哪些用户证据已经足够清楚”的基础上。每个新模块、新页面、新自动化流程，都应先写成问题假设和证据清单，再决定是否进入 MVP。

## 2. MVP 阶段

### 阶段目标

把已验证的问题转化为最小可用产品，让真实目标用户完成核心任务，并产生产品-市场匹配的早期证据。MVP 不是功能越少越好，而是只保留能验证核心价值的最小闭环。

对 OboDesk 来说，MVP 阶段的重点是证明用户会持续使用、愿意付费或愿意推荐，而不是证明团队能快速堆功能。

### 退出标准

- 一个明确用户群体在真实场景中反复使用 OboDesk 的核心能力。
- 用户能在没有创始人手把手帮助的情况下理解核心价值。
- 出现留存、付费意愿、转介绍或高质量反馈等 PMF 早期信号。
- 已经定义激活、留存、付费、推荐等关键指标，并能识别假阳性。
- 代码、文档和产品范围没有因 Agentic 编程失控而变成不可维护状态。

### 常见失败模式

- 把初始流量、朋友支持、一次性试用或社交媒体热度误判为 PMF。
- 因为 AI 开发成本低，就不断加功能，导致 MVP 范围蔓延。
- 缺少架构约束、任务边界和持久上下文，产生 Agentic 技术债。
- 忽略安全、权限、数据暴露、输入校验和依赖风险。
- 为了“看起来完整”而偏离核心验证任务。

### AI / Agent 应该做什么

- 在写代码前，帮助定义 MVP 范围：做什么、不做什么、什么证据才能改变范围。
- 生成或维护架构上下文、任务说明、约束和决策记录，例如 `CLAUDE.md`、spec、ADR、测试计划。
- 执行受控的 Agentic 编程：实现、测试、调试、重构，但只围绕已确认任务。
- 帮助建立反馈收集流程：访谈安排、bug 分诊、功能请求归类、每周摘要。
- 在上线前辅助做安全检查和基础质量审查。

### 创始人必须亲自判断什么

- MVP 的核心交互是否真的表达了 OboDesk 的价值主张。
- 哪些用户反馈应该改变产品，哪些只是范围蔓延。
- 数据是否代表 PMF，还是短期热度、渠道噪音或人工推动。
- 技术债哪些可以接受，哪些会阻碍下一阶段。
- 何时继续迭代、何时 pivot、何时退回想法阶段重新验证。

### 对 OboDesk 的实际含义

OboDesk 的 MVP 开发必须把“范围文档 + 架构上下文 + 反馈指标”作为开发前置条件。Agent 可以高效建造，但建造必须服从范围和证据。任何新增功能都应回答：它是否是核心用户拿到价值的必要条件，还是只是看起来合理的扩展。

## 3. 发布阶段

### 阶段目标

把早期 PMF 转化为可重复、可持续的增长和生产级运营能力。发布阶段不是单纯“上线”，而是证明 OboDesk 不只是一款有人喜欢的产品，而是一门可以稳定增长、可靠交付、持续运营的业务。

### 退出标准

- 增长来自可解释、可重复的渠道，而不是随机曝光或创始人个人推动。
- CAC、LTV、转化率、留存、回收周期等关键指标能够被跟踪和解释。
- 产品能承受真实生产负载，安全、可靠性、权限和数据处理可被审查。
- 支持、bug 分诊、版本规划、指标报告等流程不再依赖创始人记得去做。
- 运营系统能释放创始人的注意力，让创始人专注战略、关键客户、定位和资源配置。

### 常见失败模式

- MVP 阶段积累的技术债在生产流量和复杂需求下集中爆发。
- 创始人继续亲自处理所有问题，成为产品、支持和运营瓶颈。
- 安全和合规继续后置，直到客户数据、支付或企业采购把风险放大。
- 在核心市场还没稳定时过早扩张到新市场、新客群或新渠道。
- 把渠道增长误认为业务健康，忽略单位经济模型和留存质量。

### AI / Agent 应该做什么

- 对 MVP 代码和系统做架构审查，识别结构性弱点、测试缺口和重构优先级。
- 辅助建立轻量产品管理系统：spec 模板、冲刺节奏、bug 分诊、发布检查清单、指标周报。
- 将重复运营任务流程化：客服摘要、反馈归类、CRM 更新、指标报告、文档同步。
- 帮助做安全与合规差距分析，例如 SOC 2、GDPR、权限模型、审计日志、数据保留策略。
- 为增长系统提供研究和内容支持，但不得替代渠道验证和商业判断。

### 创始人必须亲自判断什么

- OboDesk 的增长是否真正可重复，还是依赖偶然流量或个人关系。
- 哪些运营动作可以交给系统，哪些关键判断必须保留给创始人。
- 技术债、体验债、安全债的优先级如何排序。
- 是否具备进入新市场或服务更大客户的条件。
- OboDesk 的定位、叙事和定价是否与真实价值一致。

### 对 OboDesk 的实际含义

发布阶段的 OboDesk 应把“产品周围的公司”搭起来：稳定交付、用户支持、反馈闭环、指标系统、安全治理和增长节奏。这个阶段不应继续依赖创始人的临时记忆和手工推动；但也不能把尚未稳定的流程过早自动化。

## 4. 规模化阶段

### 阶段目标

把 OboDesk 从可用产品和早期业务，扩展为有系统化增长、组织能力、客户信任和防御性优势的公司。规模化阶段的关键不是增加人头，而是把产品深度、专有数据、工作流嵌入、客户成功和组织治理变成可复利的系统。

### 退出标准

- 公司在创始人减少日常介入的情况下仍能稳定运营。
- 增长、支持、交付、财务、合规和客户成功具备可审计流程。
- OboDesk 能回答一个关键问题：如果资源充足的竞争对手复制功能，用户为什么还会留下。
- 产品具备护城河来源：领域知识、数据反馈环、深度集成、工作流锁定或品牌信任。
- 面向企业客户、合作伙伴、投资人或收购方的材料和运营能力经得起审查。

### 常见失败模式

- 把过多判断交给自动化系统，导致关键决策缺少创始人上下文。
- 创始人迟迟不放手，所有重要流程仍因等待创始人而停滞。
- 技术运营无法满足企业级客户对可靠性、支持、文档和 SLA 的要求。
- GTM 仍停留在创始人亲自销售，无法形成系统化市场和销售引擎。
- 没有把领域知识、用户数据和工作流沉淀为长期优势。

### AI / Agent 应该做什么

- 审计当前运营瓶颈，识别哪些流程可委派、可自动化、需要人类参与或必须由创始人判断。
- 帮助沉淀机构知识：产品文档、支持 playbook、销售 playbook、客户成功流程、SLA、合规材料。
- 辅助搭建 GTM 系统：细分市场、销售资料、内容管线、CRM 节奏、演示环境、API 文档。
- 分析用户行为数据，设计反馈环，让使用数据反哺产品改进。
- 识别深度集成、自动化工作流和客户切换成本，帮助形成工作流锁定。

### 创始人必须亲自判断什么

- 哪些职责必须从创始人手里交出去，哪些必须继续保留。
- OboDesk 的长期护城河到底来自哪里。
- 面向不同客户和市场时，哪些定位变化会稀释核心价值。
- 组织系统是否可靠，还是只是把混乱自动化。
- 数据、集成和工作流是否真正带来复利，而不是复杂度。

### 对 OboDesk 的实际含义

规模化阶段的 OboDesk 需要把“创始人知道的事”变成“系统可执行的上下文”。领域判断、客户经验、边缘案例、失败教训、支持策略和产品原则，都应被编码进文档、测试、流程和 Agent 可读取的上下文中。真正的规模化不是更多功能，而是更强的复利系统。

## 固定工作流

### 反证优先

每个重要决策都要先让 Agent 做反方审查：

- 为什么这个问题可能不真实？
- 为什么当前方案可能不成立？
- 哪个竞品或替代流程可能更强？
- 哪些数据会推翻我们的判断？
- 如果三个月后失败，最可能的原因是什么？

### Agentic 编程护栏

OboDesk 的 Agentic 编程应遵守以下约束：

- 每次任务前必须明确目标、范围、不可触碰区域和验证方式。
- 每个较大功能必须有 spec 或任务说明，不允许只凭聊天上下文推进。
- 架构决策、约束、项目惯例和禁止事项应沉淀为持久上下文。
- 每次会话结束后记录关键决策、假设和未解决问题。
- Agent 输出必须经过测试、审查和必要的人类判断，尤其是认证、权限、支付、数据和安全相关改动。

### 自动化前置条件

只有满足以下条件的流程才适合自动化：

- 已经人工跑通过多次；
- 输入、输出、异常情况和升级路径清楚；
- 决策规则可以被写下来；
- 自动化失败不会造成不可接受的用户、数据或业务风险；
- 有监控、日志或人工复核机制。

## 原则映射表

| 手册原则 | OboDesk 应用 | 当前应该做 | 当前不应该做 |
| --- | --- | --- | --- |
| 先验证真实问题，再建造 | 每个产品方向先写清目标用户、场景、痛点和证据 | 建立问题假设清单和用户访谈记录 | 因为 AI 能快速实现就直接开发 |
| 原型不是验证，用户证据才是验证 | demo 只用于触发真实反馈 | 用原型观察用户完成任务、记录行为和阻塞点 | 把“能跑起来”当作用户需要 |
| AI 会放大确认偏误 | Agent 必须同时产出反证、竞品威胁和失败路径 | 把反方审查加入每次产品评审 | 只让 Agent 搜支持性材料 |
| 创始人是 Orchestrator | 创始人负责问题、范围、取舍和关键判断 | 把研究、摘要、测试、分诊交给 Agent | 让创始人长期陷在重复执行里 |
| Agentic 编程要有范围、架构和持久上下文 | 所有 AI 编程都围绕 spec、架构约束和项目上下文进行 | 维护 `CLAUDE.md`、spec、决策日志和测试清单 | 开放式让 Agent 连续改代码 |
| 自动化不能早于流程稳定 | 先人工跑通支持、反馈、发布和指标流程 | 记录流程、异常和升级路径，再逐步自动化 | 把尚未定义的混乱流程自动化 |
| 对抗性思考必须成为固定工作流 | 产品、增长、架构、合规都要有 pre-mortem | 每个重要决策问“什么会证明我们错了” | 只做乐观路线图 |
| 不要把执行速度误认为商业验证 | 速度是杠杆，不是证据 | 用留存、付费、推荐和重复渠道判断进展 | 用功能数量、上线频率或页面完成度判断 PMF |
| 技术债会在发布阶段到期 | MVP 可以快，但必须知道欠了什么 | 做架构审查、测试补齐和安全检查 | 把 MVP 快捷路径带进生产规模 |
| 护城河来自复利系统 | 领域知识、数据反馈和工作流嵌入要沉淀 | 把客户边缘案例、集成和反馈环写进系统 | 只堆通用功能，忽视长期差异化 |

## 当前使用建议

在 OboDesk 的后续任务中，可以把本文档作为产品和 Agent 工作的上层上下文。任何新需求进入执行前，先判断它属于四个阶段中的哪一类，再选择对应的证据标准、Agent 分工和创始人判断点。
